# Buổi 2: Kiến trúc REST và HTTP Fundamentals

## Phần 1: 6 Nguyên tắc của Kiến trúc REST

REST (Representational State Transfer) là phong cách kiến trúc do Roy Fielding đề xuất trong luận văn tiến sĩ năm 2000. Một API được xem là RESTful khi đáp ứng đủ cả 6 ràng buộc dưới đây.

---

### 1. Client-Server (Phân tách trách nhiệm)

**Ý nghĩa:** Client đảm nhiệm phần hiển thị và tương tác người dùng; Server lo việc lưu trữ dữ liệu và xử lý nghiệp vụ. Hai bên giao tiếp qua API mà không biết chi tiết nội bộ của nhau.

**Lợi ích:**
- Server có thể scale độc lập mà không cần đụng vào client
- Hai phía phát triển song song, team front-end và back-end không chặn nhau
- Dễ thay thế hoặc nâng cấp một phía mà không ảnh hưởng phía còn lại

**Ví dụ thực tế:** App di động gọi REST API backend. Backend xử lý dữ liệu, không quan tâm giao diện mobile được thiết kế ra sao.

```python
# server.py — chỉ trả JSON, không biết gì về UI
@app.route("/users", methods=["GET"])
@require_auth
def get_users():
    return cached_response(users, max_age=30)
```

### 2. Stateless (Mỗi request tự đủ)

**Ý nghĩa:** Server không lưu bất kỳ trạng thái nào giữa các request. Mọi thông tin cần thiết để xử lý (danh tính, quyền, ngữ cảnh) phải được client đính kèm trong từng request.

**Lợi ích:**
- Scale ngang (horizontal scaling) dễ dàng — bất kỳ server nào cũng xử lý được request
- Không tốn bộ nhớ server để duy trì session
- Request độc lập → dễ reproduce lỗi, dễ log và giám sát

**Ví dụ:** Client đính token vào mỗi request thay vì đăng nhập một lần rồi dùng session:
```
Authorization: Bearer secret-token-alice
```

```python
# server.py — kiểm tra token ngay trong request, không dùng session
def require_auth(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        auth_header = request.headers.get("Authorization", "")
        if not auth_header.startswith("Bearer "):
            return jsonify({"error": "Missing Authorization"}), 401
        token = auth_header.removeprefix("Bearer ")
        if token not in VALID_TOKENS:
            return jsonify({"error": "Invalid token"}), 401
        return func(*args, **kwargs)
    return wrapper
```

### 3. Cacheable (Dữ liệu có thể tái sử dụng)

**Ý nghĩa:** Server phải chỉ rõ trong response liệu dữ liệu có được phép cache không, cache bao lâu, và khi nào cần kiểm tra lại. Client hoặc proxy trung gian có thể dùng lại bản đã lưu thay vì gọi lại server.

**Lợi ích:**
- Giảm đáng kể số lượng request đến server
- Tăng tốc độ phản hồi từ góc nhìn người dùng
- Tiết kiệm băng thông và tài nguyên tính toán

**Ví dụ headers:**
```
Cache-Control: public, max-age=30
ETag: "d41d8cd98f00b204e9800998ecf8427e"
Last-Modified: Thu, 10 Apr 2026 08:00:00 GMT
```

```python
# server.py — trả 304 khi dữ liệu chưa đổi, giúp client dùng cache
def cached_response(data, max_age: int = 30):
    etag = compute_etag(data)
    if request.headers.get("If-None-Match") == etag:
        res = make_response("", 304)
        res.headers["ETag"] = etag
        return res
    res = make_response(jsonify(data), 200)
    res.headers["ETag"] = etag
    res.headers["Cache-Control"] = f"public, max-age={max_age}"
    return res

# client.py — gửi ETag đã lưu để kiểm tra
def get_with_cache(path: str, label: str):
    cached_etag = etag_store.get(f"{BASE}{path}")
    if cached_etag:
        headers["If-None-Match"] = cached_etag
```

### 4. Uniform Interface (Giao diện thống nhất)

**Ý nghĩa:** Mọi tài nguyên đều được truy cập theo cùng một quy ước, gồm 4 yêu cầu con:
- **Định danh tài nguyên qua URI:** `/users`, `/users/1`
- **Thao tác qua representation:** client gửi/nhận JSON để thay đổi tài nguyên
- **Thông điệp tự mô tả:** header `Content-Type`, status code, method đủ để hiểu request
- **HATEOAS:** response kèm link đến các hành động liên quan (ví dụ header `Location`)

**Ví dụ thiết kế endpoint nhất quán:**
```
GET    /users        → Lấy toàn bộ danh sách
GET    /users/{id}   → Chi tiết một user
POST   /users        → Tạo user mới (trả về Location header)
PUT    /users/{id}   → Ghi đè toàn bộ thông tin user
PATCH  /users/{id}   → Cập nhật một trường cụ thể
DELETE /users/{id}   → Xoá user
```

```python
# server.py — cùng resource /users, phân biệt hành vi bằng HTTP method
@app.route("/users",         methods=["GET"])   # lấy danh sách
@app.route("/users",         methods=["POST"])  # tạo mới
@app.route("/users/<int:uid>", methods=["GET"])    # xem chi tiết
@app.route("/users/<int:uid>", methods=["PUT"])    # cập nhật
@app.route("/users/<int:uid>", methods=["DELETE"]) # xoá
```

### 5. Layered System (Kiến trúc nhiều tầng)

**Ý nghĩa:** Client chỉ biết endpoint nó đang gọi. Phía sau có thể là nhiều tầng trung gian — API gateway, load balancer, cache layer, security proxy — nhưng client không cần quan tâm và không thể phân biệt.

**Lợi ích:**
- Thêm hoặc thay đổi tầng trung gian mà không ảnh hưởng client
- Tầng cache hoặc CDN có thể xử lý một phần request trước khi vào app server
- Ẩn đi cấu trúc hạ tầng nội bộ

**Ví dụ luồng request:**
```
Client → API Gateway → Load Balancer → App Server → Database
```
Client chỉ giao tiếp với API Gateway; các tầng còn lại hoàn toàn trong suốt.

---

### 6. Code on Demand *(tuỳ chọn)*

**Ý nghĩa:** Server được phép trả về code thực thi (thường là JavaScript) để client chạy, mở rộng thêm chức năng mà không cần client biết trước. Đây là ràng buộc duy nhất không bắt buộc trong REST.

**Lợi ích:**
- Client nhẹ hơn vì không cần tích hợp sẵn mọi logic
- Có thể cập nhật hành vi client mà không cần release phiên bản mới

**Ví dụ:** Server trả về đoạn JavaScript để render widget động phía client, hoặc script kiểm tra hợp lệ form ngay trên trình duyệt.

## Phần 2: HTTP Methods

| Method    | Mô tả                                       | Idempotent | Safe   |
|-----------|---------------------------------------------|:----------:|:------:|
| `GET`     | Đọc dữ liệu từ server                       | ✓          | ✓      |
| `POST`    | Tạo resource mới                            | ✗          | ✗      |
| `PUT`     | Ghi đè toàn bộ resource                     | ✓          | ✗      |
| `PATCH`   | Cập nhật một phần resource                  | ✗          | ✗      |
| `DELETE`  | Xoá resource                                | ✓          | ✗      |
| `HEAD`    | Giống GET nhưng chỉ trả về headers, không body | ✓       | ✓      |
| `OPTIONS` | Truy vấn danh sách method mà endpoint hỗ trợ | ✓         | ✓      |

> **Idempotent:** Gọi 1 lần hay 10 lần kết quả như nhau.  
> **Safe:** Không làm thay đổi trạng thái phía server.

## Phần 3: HTTP Status Codes

### 2xx — Xử lý thành công

| Code  | Tên          | Ý nghĩa                                       |
|-------|--------------|-----------------------------------------------|
| `200` | OK           | Request thành công, có dữ liệu trả về         |
| `201` | Created      | Tạo resource mới thành công                   |
| `204` | No Content   | Thành công, không có nội dung trả về (DELETE) |

### 3xx — Chuyển hướng

| Code  | Tên               | Ý nghĩa                                    |
|-------|-------------------|--------------------------------------------|
| `301` | Moved Permanently | Resource đã chuyển sang URI mới vĩnh viễn  |
| `304` | Not Modified      | Dữ liệu chưa đổi, client dùng lại cache   |

### 4xx — Lỗi do phía Client

| Code  | Tên                  | Ý nghĩa                                          |
|-------|----------------------|--------------------------------------------------|
| `400` | Bad Request          | Request sai định dạng hoặc thiếu trường bắt buộc |
| `401` | Unauthorized         | Chưa xác thực (thiếu hoặc sai token)             |
| `403` | Forbidden            | Đã xác thực nhưng không đủ quyền truy cập        |
| `404` | Not Found            | Resource không tồn tại                           |
| `422` | Unprocessable Entity | Dữ liệu hợp lệ về cú pháp nhưng sai về logic    |
| `429` | Too Many Requests    | Client gửi quá nhiều request, bị rate limit      |

### 5xx — Lỗi từ phía Server

| Code  | Tên                   | Ý nghĩa                                        |
|-------|-----------------------|------------------------------------------------|
| `500` | Internal Server Error | Lỗi không xác định trong server               |
| `502` | Bad Gateway           | Server nhận được response không hợp lệ từ upstream |
| `503` | Service Unavailable   | Server đang quá tải hoặc bảo trì              |
| `504` | Gateway Timeout       | Upstream không phản hồi kịp trong thời gian cho phép |

## Phần 4: HTTP Headers quan trọng

### Request Headers — Client gửi lên

| Header          | Mục đích                                           |
|-----------------|----------------------------------------------------|
| `Authorization` | Đính kèm thông tin xác thực (Bearer token, Basic) |
| `Content-Type`  | Khai báo định dạng body gửi lên (`application/json`) |
| `Accept`        | Cho server biết client muốn nhận định dạng nào    |
| `User-Agent`    | Mô tả loại client đang gửi request                |
| `If-None-Match` | Gửi ETag đã lưu để kiểm tra dữ liệu có đổi chưa  |

### Response Headers — Server trả về

| Header              | Mục đích                                            |
|---------------------|-----------------------------------------------------|
| `Content-Type`      | Khai báo định dạng dữ liệu trong body trả về        |
| `Cache-Control`     | Chỉ định chính sách cache (`max-age`, `no-store`…)  |
| `ETag`              | Định danh phiên bản hiện tại của resource           |
| `Location`          | URI của resource vừa tạo (đi kèm với `201 Created`) |
| `X-RateLimit-Limit` | Số request tối đa được phép trong một khoảng thời gian |
